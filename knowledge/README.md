# Shingon knowledge service (K2 skeleton)

Permission-filtered, versioned, cited document retrieval for Conductor (reference knowledge) and, later, Foundation client apps (their own runtime knowledge). This is task **K2** of the [knowledge-base migration plan](../conductor/docs/knowledge-base/migration-plan.md#implementation-tasks-each-one-separately-reviewable). It is the [evaluation spike](../conductor/spikes/knowledge-base-evaluation/) turned into a tested package.

**What it does now:**
- tenants, principals, groups and collections (`reference` / `client-runtime`);
- repeat-safe sync from a source listing: versions, deletions, permission and supersession changes;
- import status with actionable failures;
- refusal of files containing credentials;
- keyword search with the permission filter inside the candidate query, superseded-source demotion and evidence levels;
- citations to version and page, section or sheet and cell range;
- permission-checked access to originals;
- an audit trail that stores query hashes, not query text.
- the contract's wire shapes and checks (`contract.py`), with the v1 fixture set in [`contract/kb-contract-v1.json`](contract/kb-contract-v1.json) (retrieval-contract.md §10–11);
- credentials for the HTTP layer (`auth.py`, K6 part 1): see [Credentials](#credentials-k6).

**Not yet:**
- vector and hybrid retrieval (K3) and a calibrated reranker (K4);
- Docling/OCR parsing in an isolated worker (K5);
- the HTTP server itself (K6 part 2) and the MCP adapter (K7);
- the Conductor evidence step (K8);
- backups (K9).

There is no Library of Babel data here, and none may be committed. The tests use the synthetic corpus in `tests/fixtures/`.

## Run the tests

You need Python 3.11 or later, and PostgreSQL 16 with a role allowed to `CREATE DATABASE`. Each test class creates and drops its own database.

```
cd knowledge
python -m pip install -e .
TEST_DATABASE_URL=postgres://user:pass@127.0.0.1:5432/postgres python -m unittest discover -s tests -v
```

**What the tests cover:**
- **Permissions, sync and deletion:** the spike's 21 checks as one ordered scenario. These include three sweeps of every question as every credential, judged by an independent oracle computed from the manifest, never from the database.
- **Retrieval:** the 25 labelled questions, with the known misses pinned:
  - two paraphrases, to be fixed by K3 hybrid retrieval;
  - two weak-but-not-none abstentions, to be fixed by K4 calibrated reranking.
- **Credential refusal** (secrets in files) and migration idempotence.
- **Credentials** (`test_auth.py`): what each kind of token reaches, and every way a request can fail to prove who it is.
- **Contract fixtures:** the generated fixtures are produced again in a fresh database and must match the committed file exactly, and every fixture is checked against the wire shape. After an intended change, regenerate with `KB_WRITE_FIXTURES=1` (see `tests/test_contract_fixtures.py`) and review the diff.

The fixtures under `tests/fixtures/corpus/` are generated by `tests/fixtures/make_corpus.py`, which needs LibreOffice. They are committed so CI does not.

## Credentials (K6)

Two kinds, each bound to one tenant (retrieval-contract.md §2). A token is `kb1.<id>.<secret>`, sent as `Authorization: Bearer <token>`. It is shown once when issued; the database keeps only `sha256(secret)`.

- **Project** (`auth.issue_project_credential`): a Conductor project's read token, over named **reference** collections of one tenant (§7). It asserts no user.
- **App** (`auth.issue_app_credential`): a Foundation app server's credential, issued with an **assertion key**. Each request also carries `KB-User-Assertion`, which the app server makes with `auth.sign_assertion`:
  - `<payload>.<signature>`, base64url, where the payload is `{"v": 1, "tenant", "sub", "exp", "nonce"}` and the signature is HMAC-SHA256 with the assertion key;
  - `exp` is at most 5 minutes ahead; the nonce is accepted once; the user must be a principal of the credential's tenant.

`auth.authenticate()` turns the two headers into a `Credential`, or raises `Unauthenticated`. Every refusal is the same 401 to the caller; the reason is for the server's log only. `auth.revoke()` takes effect on the next request.

The assertion key is stored as issued, because the service must check signatures with it. A copy of the database therefore lets someone forge assertions, but not call the service: that still needs a token, which is stored only as a hash.

## Decisions
